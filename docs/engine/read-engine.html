One photo in. One JSON out. Two things shown.

How the read engine turns a photo and five answers into the free read and the full Style Report, and why each stage is a separate model call.

Verdict

Five stages, each with one job, each producing a typed object. A cheap gate rejects bad photos and reads the door and heritage. An observer writes down what is visible, with no opinions. A judge makes every call from those notes only, and names the note each call rests on. A second, independent model checks each free-read line against the notes and sends failures back. A writer turns the decisions into the stylist's voice. One run produces everything; the page shows the free slice at once and unlocks the rest on payment.

The design choice that matters most: the judge never sees the photo. It works from the observation, so every claim can be checked against a record of what was actually there. That is what keeps the flattery true and stops the model inventing a jawline.

The flow

Why each stage is separate

gate

Fail fast, ask once

A photo that cannot be read costs a cheap call, not the whole pipeline. The gate returns a fixed list of issues and one friendly ask. It also reads how the person presents, so the page never asks men or women, and reads heritage with a confidence. Under 0.7, the flow asks the person. Over it, nothing is asked.

observe

A record, not a verdict

The observer is told to record and never advise. It lists undertone evidence (how skin sits next to the colours worn, jewellery, flush), every garment with colour and fit, the build only as far as the frame shows, and how far the colour read can be trusted from this light.

judge

Every call has an evidence field

The judge cannot see the photo. For each working claim it must name the observation detail it rests on. That is the mechanism behind "every line points at something in your photo", and it is what the checker tests.

check

A different model, one question each

TypeSafe Jev is a System One model: it returns a calibrated probability, not prose. For each free-read line it answers whether the notes support, contradict, or say nothing about it. A contradiction, or support below 0.6, sends the judge back with the failing lines named. Notes are stored with the report.

write

Only the words

The writer gets the decisions, not the observation, and is told it may choose words but add no facts. This keeps the voice consistent across every report and keeps claims from drifting in the rewrite.

one run

Free and paid from the same JSON

The report is generated in the same run as the free read. The page shows the free slice at once. Paying unlocks the rest in place: no second wait, no second photo, no ship date.

What "best output" rests on

  • Grounding by construction. The judge cannot describe what the observer did not record. A claim with no evidence field cannot pass the schema.
  • A second opinion from a different kind of model. The checker is not another Claude call asked "is this good"; it is a calibrated probability from a model built for judgments. Disagreement is a signal, not noise.
  • Global priors, local vocabulary. The gate reads heritage with a confidence and the flow asks when unsure. The judge uses it for skin behaviour and the garment words the person will recognise, never as a rule for what they should wear.
  • Honest confidence. Photo quality caps confidence. A dim photo still gets a read, with a retake hint on the page, and a lower number stored.
  • The eval loop. apps/web/scripts/eval-read.ts runs every stage on a folder of photos and writes each stage's JSON and a readable summary. Prompts are tuned by reading real output, starting with the two hero photos.
